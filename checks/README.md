# Что проверяют открытые задания

Проверки — ещё один способ посмотреть на результат. Код лежит в папках `01`–`24`; внутри путь совпадает с местом файла в проверяемом проекте. Запуск использует временную копию, исходники ученика остаются прежними.

Из корня курса: `python3 tools/coursecheck.py --lesson 8 --project /полный/путь/к/проекту`. Укажи свой номер и путь. По умолчанию это core. Для продолжения добавь `--track advanced`; его номера независимы.

| Недели | Что наблюдаем |
|---|---|
| 01–02 | Программа собирается, запускается и имеет непустой вывод. Смысл и авторские тексты проверяет ментор. |
| 03 | То же, плюс наличие условия и цикла; границы обсуждаются на ревью. |
| 04 | describe сохраняет название, isUrgent различает 1/2/3 с порогом 2. |
| 05 | create/get/update/remove для map[string]string; отказ не затирает старое значение. |
| 06 | pkg.Task, Complete, CRUD map[string]pkg.Task и сохранение изменённой копии. |
| 07–08 | pkg.New/Validate, ошибки из pkg: ErrInvalid/ErrConflict/ErrNotFound, отказ без изменения. |
| 09–10 | Модель в pkg, memory.Store; на 10 HTTP-приветствие. Docker/Compose09–10 и query/about смотрит ментор отдельно. |
| 11–13 | HTTP CRUD, неверный ввод, конфликт, один JSON-документ; SQL и связи на 12–13. |

Точные учебные сигнатуры видны в эталоне и тестах. Если твоё решение использует другие имена с тем же поведением, обсуди с ментором адаптацию проверок; одна форма записи не является единственно правильным решением.

## База для SQL-этапов

С 12-й недели автоматически запускается отдельный PostgreSQL Compose с уникальным именем. Проверки создают временные схемы и удаляют их, а своё окружение после работы останавливают и удаляют его учебный том. Чужие Compose-проекты не затрагиваются.

Можно передать `--database-url` или `JF_TEST_DATABASE_URL` для **выделенной тестовой базы**, где разрешено создание схем. Не указывай рабочую базу. Отсутствие соединения, схемы или обязательного файла — FAIL с ненулевым завершением. Пропущенная инфраструктура не превращается в PASS.

Набор недели повторяет сохраняемые ранее сценарии; новые формы кода получают адаптированные проверки. Тесты не требуют сохранять старый main.go после переноса в cmd. Временные поломки делай отдельно и возвращай рабочую версию перед сдачей.

★ Творческая часть не влияет на результат. Зелёный вывод подтверждает перечисленные сценарии; ментор дополнительно смотрит объяснение, новые примеры и степень помощи.

Обновление этапа 14–24: существующие проверки вызывают `Migrate(ctx)` без пути, так как SQL встроен в бинарник. SQL-helper в откатываемой транзакции читает только Up-секцию; Goose и его история выполняются в существующих Go-проверках. Этот helper не заменяет Goose и не используется при старте приложения. Runtime-порядок до HTTP, Docker-сеть и объяснение публичного договора сервиса требуют отдельного разбора с ментором. В этой редакции новые тесты не добавлялись и наборы не запускались.

Обновление HTTP/Task: модель и ошибки 10–24 перенесены в pkg. С 11 service.go/ports.go задают объектные методы; существующие сценарии memory/postgres теперь вызывают публичный TaskRepository, а не требуют имён приватных помощников. В 11–14 проверки HTTP собирают app.New(store). Сценарии и ожидания статусов сохранены, новых тестов в этом этапе нет. Query/about10, ON/WHERE/COUNT13, замена реализации 15 и порядок запуска дополнительно обсуждаются с ментором. Поведенческие наборы не запускались.
