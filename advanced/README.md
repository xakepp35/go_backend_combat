# Когда маленький JobFlow станет тесен

В основном курсе ты построил один backend и научился объяснять его работу. Здесь начинается следующий вопрос: что изменится, если обработка и доставка живут в разных процессах?

## Мост в инженерную ветку

1. Повтори путь HTTP → Service → PostgreSQL и историю транзакции из core. Назови границы гарантии подсчёта слов.
2. Сравни [договор основного проекта](../docs/PROJECT.md) с [договором распределённого движка](jobflow/docs/PROJECT.md). Task из core и принятая задача движка — разные модели; простого копирования таблицы недостаточно.
3. Открой [бинарный контракт](jobflow/docs/FRAMING.md). Заголовок, связи и тело будем вводить после работы с байтами и границами чтения.
4. Для технического знакомства начни со [снимка 11](jobflow/reference/11/README.md): это опора старой инженерной ветки, а не номер урока core. Снимки 12–24 раскрывают протокол, граф, доставку, проекции, исполнение и очистку.
5. Заведи отдельный репозиторий продолжения. Сначала воспроизведи выбранный снимок, затем исследуй одну поломку и её восстановление.

В `jobflow` сохранены 24 рабочих технических снимка, проверки и старые инженерные конспекты. Это открытый материал для работы с ментором; литературная переработка всего продолжения будет отдельным этапом. Основной курс заканчивается подготовкой к найму и пробным интервью.

Четыре сервиса: pub принимает, sub строит проекции, act исполняет, ret очищает. PostgreSQL — постоянные данные, Redis — восстанавливаемые представления, Kafka — доставка событий. Собственный протокол сохраняет исходные 128 байт и BLAKE3.
