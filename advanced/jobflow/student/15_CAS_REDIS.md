## Задача недели

Как хранить тело один раз, не объединяя разные выполнения?

**Инвариант:** Потеря Redis не уничтожает подтверждённый body.

**Перед встречей:** Обязательные проверки этапа 14 проходят в вашем репозитории. Повторите его API и ошибку, которую он уже обнаруживает.

Инструменты недели: Redis, CAS, восстановление кэша.

## Разбор

CAS адресует данные по точным байтам. Одинаковые body используют одну запись payloads, но разные Task ID означают разные намерения выполнения.

PostgreSQL сохраняет подтверждённое тело в транзакции принятия workflow. Redis хранит ускоряющую копию. При отсутствии или недоступности кэша читаем устойчивый источник. Один кэш без такого источника давал бы другую гарантию сохранности.

На чтении проверяем BLAKE3 кэшированных байтов. Повреждённую копию удаляем и восстанавливаем. TTL ограничивает жизнь копии, но не разрешает удалять устойчивое общее тело. Канонизацию JSON не вводим: пробелы и нули участвуют в хэше.

## Опорный фрагмент

Фрагмент показывает основную операцию. Имена из окружающего кода смотрите в исходнике этапа: это не отдельная готовая программа.

```go
hash := blake3.Sum256(body)
key := hex.EncodeToString(hash[:])
// PostgreSQL: payloads(key PRIMARY KEY, raw bytea)
// Redis: namespace:cas:<key>
```

## Практика на встрече

1. Назовите вход, результат и защищаемое правило для операции недели.
2. Реализуйте первый обязательный пункт [домашнего задания](../combat/15_CAS_REDIS.md). До запуска предскажите результат.
3. Воспроизведите ошибку: По одинаковому body отбрасывают задачу с новым ID.
4. Исправьте причину и объясните, какое наблюдение теперь подтверждает правило.

## Самопроверка

Почему key нельзя использовать для дедупликации выполнений?

<details>
<summary>Разбор ответа</summary>

Он идентифицирует данные, а не намерение выполнить работу.

</details>

Проверьте следующие ситуации до сдачи:

1. Одинаковые байты дают один key.
2. Повреждённая копия восстанавливается.
3. Данные доступны при отказе Redis.
