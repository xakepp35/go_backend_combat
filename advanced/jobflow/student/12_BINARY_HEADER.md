# 12. 128 байт: фиксированный заголовок

[Программа](../course/README.md) · ← [11. Отмена, backpressure и shutdown](../student/11_CANCELLATION.md) · [13. Поток, связи, тело и padding](../student/13_FRAMING.md) →

**Место в проекте:** месяц 3, Транзакции, конкурентность и заголовок. Занятие: 50 минут + 10 минут резерва. ДЗ: 8–12 часов, включая подготовку; ★ добровольна.

## Задача недели

Как разобрать неизвестный буфер без паники и чрезмерного выделения памяти?

**Инвариант:** Проверки границ и размеров предшествуют доступу к срезам.

**Перед встречей:** Обязательные проверки этапа 11 проходят в вашем репозитории. Повторите его API и ошибку, которую он уже обнаруживает.

Инструменты недели: encoding/binary, LittleEndian.

## Разбор

Go-структура в памяти не является wire-форматом. unsafe и compiler padding здесь не нужны. encoding/binary читает числа Little-Endian, а массивы ctx/dst/key копируются побайтно по таблице FRAMING.

lines задаёт полный размер в блоках по 64 байта. Сначала расширяем значение до int64, затем умножаем. Допустим размер от 128 байт до 1 MiB; блок nrefs*8 + ndeps*16 должен помещаться после заголовка.

ctx совмещает workflow ID и UUIDv7 задачи. dst адресует обработчик, key проверяет тело. nbf — момент разрешённого начала, exp — граница срока. Кратность длины 64 не гарантирует выравнивания адреса Go-среза.

## Опорный фрагмент

Фрагмент показывает основную операцию. Имена из окружающего кода смотрите в исходнике этапа: это не отдельная готовая программа.

```go
if len(buf) < 128 { return Header{}, ErrFrame }
lines := binary.LittleEndian.Uint32(buf[0:4])
size := int64(lines) * 64
if lines < 2 || size > MaxFrame { return Header{}, ErrFrame }
```

## Практика на встрече

1. Назовите вход, результат и защищаемое правило для операции недели.
2. Реализуйте первый обязательный пункт [домашнего задания](../combat/12_BINARY_HEADER.md). До запуска предскажите результат.
3. Воспроизведите ошибку: buf[96:128] читается до проверки len или память выделяется по непроверенному lines.
4. Исправьте причину и объясните, какое наблюдение теперь подтверждает правило.

## Самопроверка

Почему преобразование после lines << 6 не защищает от переполнения uint32?

<details>
<summary>Разбор ответа</summary>

Переполнение уже произошло; тип нужно расширить до арифметики.

</details>

Проверьте следующие ситуации до сдачи:

1. Длины 0–127 отклоняются.
2. 0x01020304 кодируется 04 03 02 01.
3. Огромный lines не приводит к выделению памяти.
