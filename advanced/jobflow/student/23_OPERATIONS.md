# 23. Сборка и наблюдаемость

**Место в проекте:** месяц 6, Восстановление и эксплуатация. Занятие: 50 минут + 10 минут резерва. ДЗ: 8–12 часов, включая подготовку; ★ добровольна.

## Задача недели

Как воспроизвести запуск четырёх сервисов и историю одной задачи?

**Инвариант:** Чистый запуск приводит к проверяемому результату; логи связаны по workflow/task/attempt.

**Перед встречей:** Обязательные проверки этапа 22 проходят в вашем репозитории. Повторите его API и ошибку, которую он уже обнаруживает.

Инструменты недели: Docker Compose, slog, metrics, E2E.

## Разбор

Compose описывает PostgreSQL, Redis, брокер и четыре приложения. Версии Go и образов фиксированы. Внутри контейнера localhost обозначает этот же контейнер; другие сервисы адресуются по их именам.

Readiness помогает первому запуску, но не заменяет восстановление после последующего отказа. Сначала пройдите workflow, затем остановите зависимость и проследите сохранение намерения и повтор доставки.

JSON-логи связываются по workflow/task/attempt/event. Метрики используют ограниченный набор состояний, а не Task ID в label. Сквозной тест отправляет DAG и ждёт результат через API. При отказе сохраняем короткие хвосты логов нужных процессов.

## Опорный фрагмент

Фрагмент показывает основную операцию. Имена из окружающего кода смотрите в исходнике этапа: это не отдельная готовая программа.

```bash
docker compose -f deploy/docker-compose.yml --profile app up -d --build
# Из собственного проекта:
go run ./cmd/demo
```

## Практика на встрече

1. Назовите вход, результат и защищаемое правило для операции недели.
2. Реализуйте первый обязательный пункт [домашнего задания](../combat/23_OPERATIONS.md). До запуска предскажите результат.
3. Воспроизведите ошибку: Контейнеры подключаются к localhost вместо postgres/redis/redpanda.
4. Исправьте причину и объясните, какое наблюдение теперь подтверждает правило.

## Самостоятельная работа

Продолжайте свой JobFlow по [ДЗ 23](../combat/23_OPERATIONS.md). Оценка опирается на обязательный контракт; творческая часть не нужна следующему этапу. Открывайте эталон после собственной попытки и сравнивайте причины решений, а затем меняйте решение под новое условие.
