## Задача недели

Как доказать, что отказ не повредил состояние?

**Инвариант:** Невалидный ввод отклоняется до изменения хранилища.

**Перед встречей:** Обязательные проверки этапа 03 проходят в вашем репозитории. Повторите его API и ошибку, которую он уже обнаруживает.

Инструменты недели: error, errors.Is, testing.

## Разбор

ErrInvalid означает неверные данные, ErrNotFound — отсутствие записи, ErrConflict — несовместимость с текущим состоянием. Ошибка является частью контракта. Её категорию распознаём через errors.Is, а не сравнением текста.

Validate принадлежит модели: ID и Kind не пусты, заданный exp позже nbf, тело ограничено. Отмена и недоступность базы имеют другие причины. fmt.Errorf с %w добавляет пояснение, сохраняя категорию ошибки.

Табличный тест перечисляет допустимые и недопустимые значения. После отказавшего Create проверяем не только err, но и List: неверной записи не должно быть. Проверка результата и состояния сильнее простого запуска функции.

## Опорный фрагмент

Фрагмент показывает основную операцию. Имена из окружающего кода смотрите в исходнике этапа: это не отдельная готовая программа.

```go
if err := value.Validate(); err != nil { return err }
// Только после проверки меняем состояние.
if errors.Is(err, task.ErrInvalid) { /* ошибка ввода */ }
```

## Практика на встрече

1. Назовите вход, результат и защищаемое правило для операции недели.
2. Реализуйте первый обязательный пункт [домашнего задания](../combat/04_ERRORS_TESTS.md). До запуска предскажите результат.
3. Воспроизведите ошибку: Валидация выполняется после вставки в карту.
4. Исправьте причину и объясните, какое наблюдение теперь подтверждает правило.

Почему err != nil недостаточно после неуспешного Create?

Проверьте следующие ситуации до сдачи:

1. Категории распознаются через errors.Is.
2. Неверный ввод не сохраняется.
3. Ранее работающие CRUD-сценарии сохранены.

Продолжайте свой JobFlow по [ДЗ 04](../combat/04_ERRORS_TESTS.md). Оценка опирается на обязательный контракт; творческая часть не нужна следующему этапу. Открывайте эталон после собственной попытки и сравнивайте причины решений, а затем меняйте решение под новое условие.
