# ДЗ 15. CAS, BLAKE3 и Redis-кэш

## Результат

Как хранить тело один раз, не объединяя разные выполнения? Продолжайте тот же репозиторий JobFlow.

**Защищаемое правило:** Потеря Redis не уничтожает подтверждённый body.

Бюджет: 8–12 часов с подготовкой. Ориентир: 1–2 часа на чтение и план, 5–7 на реализацию, 1–2 на проверки и объяснение. ★ выбирается по оставшемуся времени; для обязательного PASS она не требуется.

## Обязательная часть

1. Сохранять payloads по BLAKE3.
2. Добавить CAS.Get с проверкой хэша, Redis-кэшем и fallback.
3. Сохранить разные Task ID для одинакового body.
4. Проверить повреждение и недоступность Redis.

Сохраняйте ранее введённые интерфейсы и обещания. Формальные сигнатуры и крайние случаи доступны в [проверке 15](../checks/15_test.go) и [правилах проверки](../checks/README.md); зависимость инфраструктуры от домена направлена к домену.

## Критерии приёмки

1. Одинаковые байты дают один key.
2. Повреждённая копия восстанавливается.
3. Данные доступны при отказе Redis.

Из корня курса запустите:

```bash
make check LESSON=15 PROJECT=/absolute/path/to/jobflow
```

Команда должна завершиться кодом 0 и PASS обязательных проверок 01–15. Ошибка, пропуск инфраструктуры или отсутствие пакета дают FAIL. Собственные тесты добавляйте рядом с реализацией. Открытые тесты разрешено читать и запускать до сдачи.

## Что сдать

- PR или коммит со всеми обязательными изменениями и README запуска.
- Вывод автоматической проверки с номером этапа и ревизией кода.
- Краткое объяснение инварианта: где проверяется, какой отказ обнаружен, чем подтверждён результат.

## Необязательная ★

Предотвратить одновременное массовое заполнение одного отсутствующего ключа.

Не меняйте обязательный внешний контракт ради ★. В PR опишите дополнительное условие и способ проверки. Результат ★ обсуждается отдельно и не меняет PASS основной части.
