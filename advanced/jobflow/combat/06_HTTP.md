## Результат

Как дать клиенту CRUD с понятными ошибками и ограничениями? Продолжайте тот же репозиторий JobFlow.

**Защищаемое правило:** Транспорт переводит представления и ошибки; бизнес-правило остаётся в приложении.

Бюджет: 8–12 часов с подготовкой. Ориентир: 1–2 часа на чтение и план, 5–7 на реализацию, 1–2 на проверки и объяснение. ★ выбирается по оставшемуся времени; для обязательного PASS она не требуется.

## Обязательная часть

1. Реализовать api.New(repo) и маршруты черновиков из контракта.
2. Добавить ограниченное JSON-декодирование и перевод ошибок.
3. Передавать request.Context в приложение.
4. Проверить HTTP через httptest.

Сохраняйте ранее введённые интерфейсы и обещания. Формальные сигнатуры и крайние случаи доступны в [проверке 06](../checks/06_test.go) и [правилах проверки](../checks/README.md); зависимость инфраструктуры от домена направлена к домену.

## Критерии приёмки

1. Создание возвращает 201, повтор — 409.
2. Невалидный JSON возвращает 400.
3. После отказа неверный черновик отсутствует.

Из корня курса запустите:

```bash
make check LESSON=06 PROJECT=/absolute/path/to/jobflow
```

Команда должна завершиться кодом 0 и PASS обязательных проверок 01–06. Ошибка, пропуск инфраструктуры или отсутствие пакета дают FAIL. Собственные тесты добавляйте рядом с реализацией. Открытые тесты разрешено читать и запускать до сдачи.

## Что сдать

- PR или коммит со всеми обязательными изменениями и README запуска.
- Вывод автоматической проверки с номером этапа и ревизией кода.
- Краткое объяснение инварианта: где проверяется, какой отказ обнаружен, чем подтверждён результат.

## Необязательная ★

Проверить границу размера запроса и различие размеров JSON/Base64 и декодированного Body.

Не меняйте обязательный внешний контракт ради ★. В PR опишите дополнительное условие и способ проверки. Результат ★ обсуждается отдельно и не меняет PASS основной части.
