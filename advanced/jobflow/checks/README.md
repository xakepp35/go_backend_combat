# Открытая автоматическая проверка

## Запуск

Из корня курса, указывая собственный Go-модуль:

```bash
make check LESSON=08 PROJECT=/absolute/path/to/jobflow
```

Module path — `jobflow`. Требуются Go 1.27.2, Python 3, make, Docker с Compose с этапа 07 и C-компилятор с 11. `GO=/absolute/path/to/go` позволяет выбрать toolchain без установки в систему. Проверка создаёт временную копию; исходники сдаваемого проекта не меняет.

Обязательные проверки накопительные: 08 запускает 01–08. В копию добавляются открытые проверки из этой директории. Затем выполняются `go vet ./...` и `go test ./...`; с 11 включается `-race`. С 13 измеряется покрытие **бинарного пакета**, минимум 80%; fuzz seeds входят в обычный test.

```bash
python3 tools/coursecheck.py --lesson 13 --project /absolute/path/to/jobflow --fuzz
make check-all
```

`--fuzz` добавляет короткую fuzz-сессию; `check-all` проверяет все 24 независимых эталона на настоящей инфраструктуре. `go test ./...` в раннем эталоне без собственных тестов не заменяет сдачу через грейдер.

## PASS

Код 0 и строка PASS выдаются только после всех обязательных шагов. Отсутствующий Go, пакет, SQL-файл, контейнер, Redis, Kafka или упавший тест дают ненулевой код. ★ не запускается как обязательная проверка и на PASS не влияет. Покрытие не является доказательством корректности: вместе с ним проверяются конкретные отказы.

Инфраструктура — уникальный Compose-проект и свободные host-порты. После проверки удаляются его контейнеры и тома. При аварийном завершении процесса имя оставшегося проекта видно в `docker compose ls`; удаляйте только соответствующий jf-check-проект.

Режим `--infra-project NAME` явно переиспользует учебное окружение и не удаляет его. Нужны `JF_TEST_DATABASE_URL`, с 15 `JF_TEST_REDIS_ADDR`, с 16 `JF_TEST_KAFKA_BROKERS`. SQL 07 выполняется в транзакции отдельной схемы; Go-проверки БД создают и удаляют собственные схемы. Redis использует отдельные namespace, Kafka — отдельные topic. Для обычной сдачи используйте автоматическое окружение без этого параметра.

## Контракт по этапам

Публичные сигнатуры читаются непосредственно в test-файлах. Изменить внутреннее устройство разрешено; сохраняйте наблюдаемое поведение и интерфейсы потребителя. Полезно сначала выписать зависимость из импорта проверки, затем реализовать минимальный пакет.

| Этап / проверка | Обязательное наблюдение |
|---|---|
| [01. Инженерная задача и окружение](01_test.go) | Вывод содержит JobFlow. Проект собирается, vet и test завершаются успешно. Команды воспроизводятся после клонирования. |
| [02. Типы, функции и модель задачи](02_test.go) | Созданная модель сохраняет ID и Kind. Байты Body не теряются. Одинаковый Body допускается у разных ID. |
| [03. Коллекции, указатели и CRUD](03_test.go) | Дубликат сохраняет старый Body. Update изменяет, Delete удаляет запись. Изменение результата Get не меняет хранилище. |
| [04. Ошибки, валидация и тесты](04_test.go) | Категории распознаются через errors.Is. Неверный ввод не сохраняется. Ранее работающие CRUD-сценарии сохранены. |
| [05. Пакеты и границы зависимостей](05_test.go) | Сервис использует переданную реализацию. Невалидный ввод не пересекает границу записи. Домен не импортирует драйверы и HTTP. |
| [06. HTTP как граница приложения](06_test.go) | Создание возвращает 201, повтор — 409. Невалидный JSON возвращает 400. После отказа неверный черновик отсутствует. |
| [07. SQL с нуля и первая миграция](07_test.go) | Миграция выполняется на пустой схеме. Строка создаётся, читается и изменяется. Настоящий PostgreSQL отклоняет дубликат. |
| [08. Go и PostgreSQL-адаптер](08_test.go) | Второе подключение видит те же байты. Повтор миграции безопасен. Дубликат и отсутствие ID распознаются. |
| [09. Транзакция и намерение события](09_test.go) | Успех даёт одно намерение. Отказ второго шага откатывает первый. Конфликт ID не добавляет новое намерение. |
| [10. Горутины и ограничение параллелизма](10_test.go) | Все переданные функции завершаются. Активность не превышает workers. Неверный workers вызывает ошибку. |
| [11. Отмена, backpressure и shutdown](11_test.go) | Пустая очередь не блокирует остановку. Работники завершены перед возвратом Run. Конкурентные проверки проходят с -race. |
| [12. 128 байт: фиксированный заголовок](12_test.go) | Длины 0–127 отклоняются. 0x01020304 кодируется 04 03 02 01. Огромный lines не приводит к выделению памяти. |
| [13. Поток, связи, тело и padding](13_test.go) | Пустое и нулевое тело проходят roundtrip. Усечения отклоняются. После Skip читается следующий фрейм. |
| [14. DAG и принятие workflow](14_test.go) | Цепочка и ромб принимаются. Цикл и неизвестный ref отклоняются. Повтор не создаёт новый workflow. |
| [15. CAS, BLAKE3 и Redis-кэш](15_test.go) | Одинаковые байты дают один key. Повреждённая копия восстанавливается. Данные доступны при отказе Redis. |
| [16. Kafka и доставка Outbox](16_test.go) | При отказе событие остаётся. После восстановления оно читается из Kafka. Delivered следует после успеха публикации. |
| [17. sub и восстанавливаемые проекции](17_test.go) | Версия 1 не откатывает версию 2. Повтор безопасен. После удаления проекция восстанавливается. |
| [18. Redis Streams и потерянный потребитель](18_test.go) | Готовая задача создаёт сигнал. Pending передаётся новому потребителю. ACK убирает pending-запись. |
| [19. act и право на попытку](19_test.go) | Из восьми claim успешен один. Чужой token отклоняется. Обработчик sum возвращает ожидаемое значение. |
| [20. Время и планирование](20_test.go) | До nbf claim отклоняется. Незавершённая зависимость блокирует запуск. На exp результат отклоняется, задача истекает. |
| [21. Повторы и идемпотентный эффект](21_test.go) | Эффект не удваивается. Повтор result идемпотентен, изменение конфликтует. Паника изолирована, квоты проверяются. |
| [22. ret и безопасная очистка](22_test.go) | Недоставленное событие блокирует удаление. Общее тело живёт до снятия всех ссылок. Один общий blob удаляется один раз. |
| [23. Сборка и наблюдаемость](23_test.go) | Команды собираются. Задача проходит Kafka и Streams до результата. Сбой даёт диагностические логи. |
| [24. Защита проекта](24_test.go) | Разные ID с одинаковым body независимы. Изменённый вход того же ID конфликтует. Локальная коллизия ref отклоняется. |

## Инфраструктурные случаи

- 07–09: SQL действительно выполняется в PostgreSQL; новая связь видит запись; сбой второго INSERT откатывает оба изменения.
- 15: повреждённый CAS и недоступный Redis восстанавливаются из PostgreSQL с проверкой хэша.
- 16–18: настоящий Kafka producer/consumer; недоступная публикация сохраняет Outbox; устаревшая проекция не откатывает version; pending Stream передаётся другому consumer.
- 19–21: конкурентный claim даёт одну действующую попытку; старый token не принимается; nbf/exp/dependencies проверяются с искусственными часами; повтор эффекта не увеличивает counter; брошенные попытки ограничены.
- 22: GC защищает недоставленные события, общий CAS и живого потомка; повторная очистка безопасна.
- 23: собираются и запускаются четыре настоящих процесса с реальными PostgreSQL, Redis и Kafka. Сценарий проходит HTTP → Outbox → Kafka → sub → Streams → act → result.
- 24: один body допускает разные Task ID; изменённый повтор конфликтует; коллизия локального ref отклоняется.

[Векторы бинарного формата](fixtures/README.md) дополняют табличные и потоковые тесты. Грейдер также проверяется намеренной поломкой инвариантов: [check_mutants.py](../tools/check_mutants.py) обязан увидеть FAIL, а не потерять ошибку.

## Проверка через GitHub Actions

В собственном starter CI собирает Go-модуль и запускает его тесты. Полная проверка сдачи находится в [workflow Grade submitted JobFlow](../../../.github/workflows/grade.yml): ментор задаёт repository, точную revision, track=advanced и lesson. Workflow курса [Course contracts](../../../.github/workflows/course.yml) проверяет материалы и все эталоны. Результат запуска привязывайте к ревизии PR.

Короткая устная проверка дополняет автоматику: ученик объясняет один инвариант и меняет одно условие. Эталон открыт и не является способом скрыть пробелы в понимании.
