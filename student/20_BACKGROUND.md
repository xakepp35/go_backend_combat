# 20. Что происходит с задачей после отправки?

[Карта курса](../course/README.md) · [← Предыдущий урок](19_CONTEXT.md) · [Следующий урок →](21_OPERATIONS.md)

## «Принято» и «готово» — два разных момента

Представь заказ отчёта: человек отправил текст, сервис должен посчитать слова. Можно дождаться результата в HTTP. А можно принять работу, дать ID и позволить спросить результат позже.

Добавим отдельный ресурс **job**, машинное фоновое задание. Наши человеческие дела в `/tasks` остаются. У задания будут ID, текст, состояние, число попыток и результат. Единственный зарегистрированный обработчик основного курса — подсчёт слов. Произвольные команды из запроса не выполняются.

Состояния:

```text
queued → running → done
             ↓
          queued  (разрешённый повтор)
             ↓
          failed  (ошибка окончательна или попытки исчерпаны)
```

Стрелки из running зависят от результата текущей попытки. Точную таблицу переходов смотри в [договоре проекта](../docs/PROJECT.md).

## У ожидающей работы появилась постоянная память

`POST /jobs` сохраняет запись в PostgreSQL, `GET /jobs/id` показывает состояние. Исполнители периодически ищут ожидающее задание. Один атомарный UPDATE переводит выбранное queued в running и увеличивает attempts; конкурирующая попытка взять уже занятое задание не получит его.

В процессе работают два исполнителя. База хранит ожидание, поэтому перезапуск не теряет принятые задания. Для основного курса запускаем **один экземпляр приложения**. На старте, до workers, незавершённые running возвращаются в очередь либо становятся failed, если лимит исчерпан. Эта учебная процедура восстановления предполагает, что прежний процесс уже остановлен.

При аварии после вычисления, но до записи результата подсчёт может выполниться повторно. Для чистого вычисления это допустимо. Для списания денег понадобился бы отдельный договор побочного эффекта — его изучает продолжение.

## Когда повторять

Повтор, retry, нужен для временной ошибки. Неверный ввод от повторения не исправится. Максимум три попытки и небольшая пауза ограничивают расход ресурсов. Остановку приложения обрабатываем как остановку, а не маскируем бесконечными повторами.

Сам подсчёт слов — детерминированное вычисление:

```go
func CountWords(ctx context.Context, text string) (string, error) {
    if err := ctx.Err(); err != nil { return "", err }
    return strconv.Itoa(len(strings.Fields(text))), nil
}
```

Фрагмент из `internal/jobs`; ему нужны импорты context, strconv, strings. Поведение временной ошибки проверяем подставным обработчиком, который сначала отказывает, затем успешно считает. Рабочий обработчик не притворяется случайно сломанным.

## А если клиент отправил запрос второй раз?

Повтор с тем же ID и тем же текстом возвращает существующее задание. Тот же ID с другим текстом — конфликт. Это **идемпотентное принятие**: повтор одной просьбы не создаёт ещё одну работу. Уникальный ключ базы помогает сохранить правило даже при двух одновременных запросах.

Детерминированность и идемпотентность — разные свойства. Одинаковый результат чистой функции не гарантирует однократную отправку письма или перевод денег.

Проверь путь целиком: принять → увидеть queued/running → получить done и результат → повторить запрос → перезапустить → прочитать прежний результат. Потом отдельно исследуй сбой между шагами. Вот теперь наш маленький JobFlow действительно выполняет фоновую работу.
