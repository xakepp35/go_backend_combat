# 16. Как сохранить два изменения вместе?

[Карта курса](../course/README.md) · [← Предыдущий урок](15_INTERFACES.md) · [Следующий урок →](17_GOROUTINES.md)

## Две успешные строки ещё не одна успешная операция

Создаём задачу и событие `created`. Первая вставка прошла. Вторая завершилась ошибкой. Теперь задача есть, а обещанной истории нет. Пользователь просил одно действие, а получил половину.

**Транзакция** объединяет изменения базы в одну группу: либо фиксируются все, либо ни одно. Свойство «всё или ничего» называют **атомарностью**.

Сначала руками в psql:

```sql
BEGIN;
INSERT INTO tasks(id, title, priority) VALUES ('tx-a', 'Купить чай', 1);
INSERT INTO task_events(task_id, action) VALUES ('missing', 'created');
ROLLBACK;
SELECT id FROM tasks WHERE id = 'tx-a';
```

Вторая вставка нарушит внешний ключ. После `ROLLBACK` новая задача отсутствует. Повтори с правильным `task_id` и `COMMIT`: сохранятся обе записи.

`BEGIN` начинает транзакцию, `COMMIT` фиксирует, `ROLLBACK` отменяет. Ошибка внутри PostgreSQL-транзакции обычно оставляет её в состоянии отказа до отката; продолжать команды как будто ничего не случилось нельзя.

## Тот же договор в Go

В реализации `postgres.Store.Create` заменим отдельную вставку:

```go
tx, err := s.pool.Begin(ctx)
if err != nil { return err }
defer tx.Rollback(context.Background())

_, err = tx.Exec(ctx,
    "INSERT INTO tasks(id,title,priority,done) VALUES($1,$2,$3,$4)",
    t.ID, t.Title, t.Priority, t.Done)
if err != nil { return translate(err) }
_, err = tx.Exec(ctx,
    "INSERT INTO task_events(task_id,action) VALUES($1,'created')",
    t.ID)
if err != nil { return translate(err) }
return tx.Commit(ctx)
```

Это фрагмент метода, не отдельный `main`. **Оба запроса выполняются через `tx`**. Если второй отправить через `s.pool`, он окажется вне этой транзакции.

Отложенный Rollback служит уборкой при раннем выходе; после успешного Commit повторный откат уже ничего не отменит. В полной реализации у уборки есть короткий независимый срок ожидания, чтобы отменённый запрос не мешал освободить соединение.

## Где провести границу

В одну транзакцию входят связанные изменения, необходимые для обещанного результата. Держать её открытой, пока человек читает страницу или внешняя сеть отвечает минуту, неудобно: соединение и блокировки заняты.

Транзакция базы не откатывает отправленное письмо. Наше изменение задачи и истории находится внутри одной PostgreSQL. Как согласовывать базу с другими системами, изучим в продолжении через Outbox.

## Проверяем настоящий откат

В отдельной тестовой схеме добавь ограничение, которое отклонит событие `created`. Вызови Create и проверь, что задачи нет. Удали тестовую схему после проверки. Так мы проверяем отказ именно второго шага, а не только дубликат первого.

Полезно также проверить успешный путь: задача и одно событие существуют вместе. Количество событий читаем отдельным SELECT.

В конце проведём короткое пробное интервью: объясни JOIN, параметр запроса, интерфейс хранилища и эту транзакцию на своём коде. Если слово забылось, начни с примера — смысл важнее скорости вспоминания термина.
