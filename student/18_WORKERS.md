# 18. Как распределить работу между исполнителями?

[Карта курса](../course/README.md) · [← Предыдущий урок](17_GOROUTINES.md) · [Следующий урок →](19_CONTEXT.md)

## Сто посетителей, три сотрудника

Нам нужно обработать много задач. Запускать неограниченное число исполнителей — всё равно что впустить всех посетителей за стойку. Число сотрудников и место в очереди конечны.

**Worker pool** — несколько исполнителей, получающих работу из общей очереди. В Go очередь удобно выразить **каналом**: через него можно передать значение другой горутине.

Простая самостоятельная команда `cmd/workers/main.go`:

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    jobs := make(chan string, 2)
    var wg sync.WaitGroup
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for title := range jobs {
                fmt.Println("Обработали:", title)
            }
        }()
    }
    jobs <- "Купить чай"
    jobs <- "Записаться к врачу"
    jobs <- "Позвонить другу"
    close(jobs)
    wg.Wait()
}
```

Запусти `go run ./cmd/workers`. Каждое дело обработается один раз, порядок строк может меняться.

`chan string` передаёт строки. Число 2 — вместимость буфера. Отправка `<-` ждёт свободного места, если буфер заполнен. `range jobs` получает значения до закрытия канала и опустошения буфера.

## Кто закрывает дверь

Канал закрывает тот, кто знает, что отправок больше не будет. Здесь это `main`, единственный отправитель. Если каждый worker решит закрыть канал, один закроет его, а остальные могут попытаться отправить или закрыть повторно и получить панику.

Получателю не нужно закрывать канал, чтобы перестать читать; но тогда надо договориться, как остановятся отправители. В следующем уроке поможет отмена через context.

Закрытие не удаляет уже отправленные элементы. Получатель ещё прочитает буфер, затем цикл закончится.

## Очередь тоже ограничивает нагрузку

Если исполнители не успевают, отправитель ждёт. Это **обратное давление**, backpressure. Оно не делает работу быстрее, зато не позволяет молча накапливать бесконечный объём в памяти.

В пользовательском HTTP можно выбрать другой договор: подождать с ограничением времени или вернуть понятную перегрузку. Выбор зависит от требований. Для нашей локальной команды ожидание допустимо.

Не начинай с числа 1000 исполнителей. Выбери два, посмотри, где проходит время и что ограничивает работу. Количество CPU, ожидание сети и число соединений базы дают разные ограничения.

## Из команды в повторно используемую функцию

В эталоне те же действия вынесены в `internal/pool.Run`: функция принимает число исполнителей, входной канал и обработчик. Context уже встречался в запросах базы; пока передаём его обработчику. Эту первую версию завершает закрытие конечного входа. На следующем уроке добавим отмену ожидания через select.

## Как проверить ограничение

В тестовом обработчике увеличь защищённый счётчик активных работ на входе и уменьши на выходе. Сохрани максимум. Для двух workers максимум должен быть не больше двух, а после завершения активных — ноль.

Одного количества напечатанных строк для этого мало: оно ничего не говорит о пике одновременной работы.
