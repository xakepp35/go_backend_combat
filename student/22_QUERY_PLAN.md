# 22. Почему запрос стал медленным?

[Карта курса](../course/README.md) · [← Предыдущий урок](21_OPERATIONS.md) · [Следующий урок →](23_JOB_SEARCH.md)

## «Тормозит» сначала превращаем в наблюдение

На пяти задачах запрос отвечал быстро. На большом списке — заметно дольше. Прежде чем ставить Redis, выясним, что происходит в PostgreSQL.

**Индекс** — дополнительная структура, помогающая находить строки по определённым условиям. Как алфавитный указатель: найти фамилию можно быстрее, чем читать всю книгу. Но указатель занимает место и должен обновляться при изменениях.

Нельзя решить, полезен ли индекс, только по красоте его названия. Нужен запрос, данные и наблюдение плана.

## Один запрос, один эксперимент

На отдельной учебной базе с задачами выполни:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM tasks
WHERE done = false
ORDER BY priority DESC, id
LIMIT 20;
```

`EXPLAIN` показывает выбранный план. `ANALYZE` действительно исполняет запрос и добавляет измерения. Для SELECT здесь это ожидаемо; с UPDATE или DELETE такой эксперимент реально изменил бы данные.

`Seq Scan` — последовательный просмотр строк. `Index Scan` — доступ с помощью индекса. В плане есть ожидаемое и фактическое количество строк, шаги сортировки и затраты времени. Не нужно понимать все поля в первый вечер: найдём, сколько строк просмотрено ради двадцати результатов.

Добавим индекс отдельной миграцией:

```sql
CREATE INDEX tasks_open_priority_idx
ON tasks (priority DESC, id)
WHERE done = false;
```

Он относится только к незавершённым задачам и поддерживает нужный порядок. Повтори тот же SELECT и сохрани оба плана.

## Почему на трёх строках план мог не измениться

Для маленькой таблицы полный просмотр может быть дешевле переходов по индексу. Планировщик выбирает по данным и статистике, а не обязан демонстрировать новый индекс.

В `sql/benchmark.sql` есть подготовка отдельной учебной выборки и `ANALYZE tasks`, обновляющий статистику. Выполняй её в выделенной базе, потому что она добавляет множество демонстрационных строк. Объём, условия запроса и измерения запиши рядом с выводами.

Не требуем магического «ускорения в десять раз». Хороший результат — честное объяснение наблюдения, включая случай, когда индекс не помог.

**Избирательность условия**, selectivity, связана с долей подходящих строк. Если условию подходит одна из тысячи, индекс может избавить от большого просмотра; если подходят почти все, последовательный доступ часто дешевле. Это объяснение дополняет конкретный план, а не заменяет измерение.

## Цена решения

Индекс занимает место и добавляет работу при записи. Если запрос почти не используется, цена может перевесить пользу. Сначала стоит проверить сам запрос: нужны ли все столбцы, ограничен ли объём, есть ли нужное условие.

Кэш — отдельный механизм со сроком жизни и вопросом устаревания. Нашему текущему эксперименту он не требуется. В продолжении рассмотрим Redis после появления соответствующей потребности.

На собеседовании начни ответ с процедуры: воспроизвести медленный запрос, посмотреть план на подходящих данных, предложить изменение и повторить измерение. Это полезный инженерный навык даже тогда, когда название нужного индекса ещё не пришло в голову.
