# Ответ начинается с понятного примера

Эти пояснения дополняют исходные ответы. После чтения закрой страницу и расскажи своими словами.

## №1–4: пакет, модуль и запуск

Пакет — связанный Go-код в одной директории. Модуль — проект из пакетов с go.mod. В нашей первой программе пакет main обозначает запускаемую команду. `go mod init` создаёт go.mod; в первом запуске мы написали тот же небольшой файл руками. `go run` собирает и сразу запускает, `go build` оставляет исполняемый файл.

Уточнение: перенос функции между файлами одного пакета не создаёт новую границу доступа. Это увидим на уроке 9.

## №5, 7–9: значение и его тип

`priority := 2` даёт переменную типа int. `:=` помог определить тип, но не отключил проверку типов. Присвоить ей строку «срочно» нельзя. Если объявить `var done bool`, значение будет false. У string нулевое значение — пустая строка, у int — 0.

Уточнение: нулевое значение корректно для языка, но может быть недопустимо для правила приложения, например приоритет 0.

## №22–29: список и поиск

Срез хранит последовательность значений; len говорит о числе доступных элементов. map ищет значение по ключу. Чтение `value, ok` позволяет различить отсутствующий ключ и нулевое значение. Результат append присваиваем обратно: функция могла вернуть срез с новым местом хранения.

Уточнение: порядок обхода map не обещан. Для отсортированного ответа нужна явная сортировка.

## №13–18: карточка и копия

Task собирает поля одной задачи. При копировании Task с простыми полями получаются отдельные значения. Метод с `*Task` меняет то значение, на которое указывает receiver. Скопировать указатель и скопировать саму структуру — разные действия.

Уточнение: указатель не добавляет автоматической защиты от одновременных изменений.

## №30–31: вход и результат

Функция describe принимает название и приоритет, возвращает строку. Вывод делает вызывающий код. Несколько результатов позволяют вернуть значение и объяснение неудачи: `(Task, error)`.

## №45, 47–49: неудача и её категория

Validate проверяет поля. ErrInvalid обозначает категорию, сообщение уточняет, какое поле не подошло. Обёртка `%w` сохраняет категорию, errors.Is её узнаёт. Текст можно улучшить, не меняя договор вызывающего кода.

Уточнение: напечатать ошибку и продолжить запись — обычно нарушить ожидаемое поведение отказа.

## №51–59: сменный исполнитель

Service просит сохранить задачу через нужные ему методы. memory и postgres выполняют этот договор разными способами. Интерфейс объявляем рядом с потребителем, а конкретную реализацию передаём из main. Добавлять в него весь API драйвера незачем.

## №61–65: откуда известно, что получилось

Тест создаёт условия, вызывает действие и сравнивает результат. Для дубликата важно не только получить ошибку, но и прочитать прежнюю запись. Это проверка наблюдаемого поведения. После изменения тест помогает заметить возвращение старой ошибки — регрессию.

## №171–174, 221, 251: правила базы

Первичный ключ различает строки, внешний связывает событие с существующей задачей, NOT NULL запрещает отсутствие значения. Транзакция объединяет задачу и историю: при отказе второй записи откатываются обе. Атомарность означает «всё или ничего» для этих изменений базы.

## №331–333: повтор одной просьбы

Повторное принятие одного job ID с тем же текстом возвращает прежний job. Новый job не появляется. Одинаковый результат подсчёта слов — детерминированность. Однократный внешний платёж потребовал бы отдельной защиты побочного эффекта.

## №401, 407–413: сеть и правила приложения

Обработчик читает HTTP, вызывает знакомое действие и переводит результат в ответ. Неизвестная задача даёт 404, конфликт ID — 409. Правило Task не знает числа 404: это задача сетевой границы.

## №421–425: время ожидания

r.Context связывает работу с запросом. Отмена проходит вниз в Service и запрос базы. Если заменить context на Background, связь потеряется. При собственной фоновой работе создаём отдельный жизненный цикл приложения.

## №404: данные запроса

DTO — структура данных для передачи через границу. В HTTP она описывает получаемые поля. У наших tasks это простой набор полей; у jobs отдельная входная структура разрешает только id/text и не даёт клиенту назначить status или attempts.

## №431: прикладной слой

Application layer — код сценария приложения. Наш Service координирует создание задачи: проверяет правила и вызывает хранилище. HTTP читает и пишет сетевое представление, а PostgreSQL Store исполняет SQL. Разделение помогает понять, какое изменение куда относится.
