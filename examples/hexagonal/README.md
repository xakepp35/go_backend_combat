# Один проход через границы JobFlow

Это отдельный небольшой пример нового архитектурного договора, введённого в первой части. На первом занятии смотри карту; после функций найди входы и результаты; после структур и интерфейсов разбери код полностью. Здесь только создание задачи и чтение списка: весь CRUD ради демонстрации границ не нужен.

[Объяснение ролей](../../docs/PROJECT_FLOW.md) · [Плакат](../../posters/core/HEXAGONAL.svg)

## Путешествие одного запроса

`POST /tasks` → `api` разбирает JSON → `pkg.TaskService.Create(ctx, req)` → `app` проверяет `Task.Validate` → `pkg.TaskRepository.Insert(ctx, req)` → `memory` атомарно проверяет уникальность ID и сохраняет → объект ответа возвращается через API.

Публичный договор расположен в `pkg`: модель, именованный тип приоритета, константы, запросы/ответы, ошибки, сервисный интерфейс и выходной порт в `ports.go`. API импортирует `pkg`, его конструктор принимает `pkg.TaskService`. Он не импортирует `app` и не знает тип конкретного хранилища. `main` соединяет реализации.

## Как открыть пример

В терминале перейди в эту папку, затем выполни:

```sh
go run ./cmd/jobflow
```

`go.mod` уже существует — `go mod init` повторять не нужно. Сервер слушает только `127.0.0.1:8080`; Docker, Redis и база здесь не требуются. Остановка — `Ctrl+C`.

Во втором терминале Ubuntu/macOS:

```sh
curl -i http://127.0.0.1:8080/tasks
curl -i -X POST http://127.0.0.1:8080/tasks -H 'Content-Type: application/json' -d '{"id":"tea","title":"Купить чай","priority":2}'
curl -i http://127.0.0.1:8080/tasks
```

Для Windows PowerShell тело лучше сформировать инструментом:

```powershell
$taskBody = @{ id = "tea"; title = "Купить чай"; priority = 2 } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8080/tasks -ContentType 'application/json; charset=utf-8' -Body ([System.Text.Encoding]::UTF8.GetBytes($taskBody))
Invoke-RestMethod -Uri http://127.0.0.1:8080/tasks
```

## Обещанное поведение

| Сценарий | Ожидаемый результат |
|---|---|
| Пустой список | 200, `{"tasks":[]}` |
| Создание корректной задачи | 201, `{"task":{"id":"tea","title":"Купить чай","priority":2,"done":false}}` |
| Повтор ID | 409, состояние не изменилось |
| Пустое название или приоритет 4 | 400, состояние не изменилось |
| Несколько задач | 200, объект со списком, упорядоченным по ID |
| Неизвестное поле или второй JSON-документ | 400 |

## На что посмотреть в коде

- Входной договор: [pkg/service.go](pkg/service.go), [requests.go](pkg/requests.go), [responses.go](pkg/responses.go).
- Инварианты: [pkg/task.go](pkg/task.go), вызов проверки в [app/service.go](internal/app/service.go).
- Выходной порт: [pkg/ports.go](pkg/ports.go), атомарная реализация в [memory/store.go](internal/memory/store.go).
- HTTP-преобразование: [api/api.go](internal/api/api.go), сборка в [main.go](cmd/jobflow/main.go).

Запись `var _ pkg.TaskService = (*Service)(nil)` заставляет компилятор проверить, что реализация удовлетворяет интерфейсу. Это не проверка поведения. Мьютекс защищает совместный доступ к карте; на теме конкурентности разберём, почему проверка уникальности и вставка находятся под одной блокировкой.

Ограничения примера: данные живут до остановки процесса; нет авторизации, пагинации и graceful shutdown. gRPC-адаптер не реализован: для него потребуются protobuf-контракты и преобразование в те же сервисные запросы. Объектные ответы уже дают устойчивое место для развития прикладного договора.

Снимки поздних уроков будут переноситься на этот стандарт по мере переработки соответствующей части. Этот пример не заменяет их прежний внешний HTTP-протокол автоматически.
