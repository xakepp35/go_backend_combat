# Если в базе остался старый course_migrations

Эта памятка нужна только тем, кто запускал предыдущие эталоны 14–24. Для чистой базы приложение само применяет Goose; отдельного мигратора нет.

Ранние версии учитывали **имена файлов** в `course_migrations`. Goose учитывает числовые версии в `goose_db_version`. Переименовать таблицу недостаточно. Приложение останавливает запуск при обнаружении старой истории, сохраняя данные. Не удаляй том и не заполняй новую историю номерами наугад.

## Путь с сохранением исходной базы

1. Останови приложение и все записи в старую базу. Зафиксируй версию кода и список применённых миграций. Оставь PostgreSQL работающим.
2. Сделай `pg_dump` старой базы и сохрани файл вне контейнера/тома; проверь возможность восстановления в отдельную базу. Это работа с данными: подготовь место и понятное имя файла. Команда зависит от имени Compose-проекта и твоего DB name; ментор помогает собрать её до выполнения.
3. Создай **новую пустую базу**, например `jobflow_goose`. Исходную `jobflow` не меняй. Укажи новый DB name в `DATABASE_URL` новой сборки и дай ей создать схему встроенными миграциями; после готовности останови приложение, оставив postgres.
4. Сравни старую и новую схему предметных таблиц через `pg_dump --schema-only`. Составь явный список таблиц: `tasks`, `task_events`, а с 20 — `jobs`. Если схемы расходятся, подготовь преобразование данных под эту конкретную версию. Не импортируй старый DDL поверх нового.
5. При совпадающем формате экспортируй **данные выбранных предметных таблиц** через `pg_dump --data-only --no-owner --no-privileges --table=...`. Восстанови их в новую базу с остановкой при первой ошибке; сохрани вывод и проверь последовательности identity. Таблицы `course_migrations` и `goose_db_version` из старого дампа не переносим. Для фоновых jobs отдельно реши, какие задания можно безопасно повторить: импорт `queued` приведёт к их выполнению после запуска.
6. Проверь количество записей, несколько связанных задач и состояние jobs. Запусти приложение с новым DSN. Старую базу и резервную копию сохраняй до завершения проверки переноса.

Здесь нет универсальной команды «всё починить»: переход затрагивает существующие данные, которые могут отличаться от эталона. Лучше один осознанный перенос с ментором, чем автоматическое объявление незнакомой схемы правильной. Для одноразовой пустой лаборатории можно создать новую базу без переноса; старую удаляй только отдельным осознанным решением.
