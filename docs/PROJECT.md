# JobFlow основного курса: что обещает приложение

> Здесь описан внешний протокол текущих снимков уроков 11–24. Task-сервис во всех этих снимках использует [объектные контракты pkg](PROJECT_FLOW.md). Публичный объект ответа сервиса и JSON-представление HTTP — разные границы. Блок фоновых Job с 20 ждёт отдельного пересмотра.


Первые версии показывают дело в терминале. С урока 11 у человеческих задач есть HTTP API. С урока 20 отдельно появляется машинное задание подсчёта слов. Программа запускается одним экземпляром, PostgreSQL хранит постоянные данные.

## Человеческая задача

`Task`: `id` — непустая строка, `title` — непустой после TrimSpace текст, `priority` — 1..3, `done` — bool. ID — устойчивая метка, название можно менять. Память/БД не должны хранить неверную задачу.

| Запрос | Успех | Отказ |
|---|---|---|
| POST /tasks с Task | 201, Task | 400 неверный ввод, 409 занятый ID |
| GET /tasks | 200, JSON-массив по ID | 500 ошибка хранилища |
| GET /tasks/{id} | 200, Task | 404 |
| PUT /tasks/{id} с Task | 200, Task | 400 неверный ввод/другой ID, 404 |
| DELETE /tasks/{id} | 204 | 404 |
| POST /tasks/{id}/complete | 200, Task с done=true | 404 |
| GET /healthz | 200, объект status | 503 недоступна база |

У PUT пустой id в теле заполняется из пути; другой непустой id отклоняется. Complete можно повторить: выполненная задача остаётся выполненной. Пустой список возвращает `[]`, не null. В JSON-запросе один документ, известные поля, максимум 64 KiB. Ошибки — JSON-объект `error`; внутренние подробности 500 идут в журнал.

С урока 11 API вызывает pkg.TaskService, а app зависит от pkg.TaskRepository. Модель и общие ошибки находятся в pkg и не импортируют HTTP или драйвер. На 15 подробно разбираем уже работающие границы. С урока 16 Insert в PostgreSQL атомарно сохраняет задачу и одно событие created. Чтение не создаёт данные.

## Фоновое задание с урока 20

`POST /jobs` принимает `{"id":"report-1","text":"чай хлеб молоко"}`. Пустые/пробельные ID и текст отклоняются. Первое принятие — 202 и Job. Повтор с тем же ID и тем же исходным текстом — 200 с существующим Job; изменённый текст — 409.

`GET /jobs/{id}` — 200 с Job или 404. Job содержит id, text, status, attempts, result, error. Результат — строка с числом слов; слова выделяются `strings.Fields`. Исходный текст сравнивается без нормализации.

| Событие | Переход |
|---|---|
| Принятие | queued, attempts=0 |
| Исполнитель получил право | queued→running, attempts+1 |
| Успех | running→done с result |
| Временная ошибка и attempts<3 | running→queued после ограниченной паузы |
| Окончательная ошибка или attempts=3 | running→failed |
| Старт после остановленного процесса | running→queued либо failed при исчерпанном лимите |

Не более двух исполнителей в обычной конфигурации. Задания выбираются из БД атомарно. На остановке ждём workers перед закрытием пула. Если процесс аварийно завершился, на следующем старте восстановление выполняется до запуска исполнителей.

Повторяемость чистого вычисления делает восстановление допустимым. Гарантия однократного внешнего побочного эффекта сюда не входит. У приложения один владелец восстановления — один процесс. Для нескольких экземпляров нужны иной протокол владения и fencing из продолжения.

## Окружение и схема данных

Docker/Compose вводятся на 09, PostgreSQL всегда в контейнере. SQL 12–13 выполняется в jobflow_lab; схема приложения jobflow с 14 управляется встроенным Goose/v3. Все прикладные SQL-запросы идут через native pgxpool/v5. Порядок старта: подключение/Ping → Goose с session advisory lock → восстановление jobs с 20 → обработчики/HTTP. Ошибка до готовности завершает процесс неуспешно. SQL не читается с диска runtime и не требует отдельного мигратора. Подробности: [PostgreSQL](POSTGRES.md).
