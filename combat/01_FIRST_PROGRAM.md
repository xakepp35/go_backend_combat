# 01. Практика: первая версия, которую можно принять

[Карта курса](../course/README.md) · [Следующий урок →](02_VALUES.md)

## Задача: личный план на утро

Сделай JobFlow, который показывает заголовок и **три твоих дела в выбранном порядке**. Здесь самостоятельная работа — договориться о поведении, получить воспроизводимый запуск и найти причину намеренной поломки.

**Ориентир: 1,5–2,5 часа** с настройкой. Если окружение уже готово, нормально закончить раньше. Не нужно досиживать до нормы.

| Работа | Ориентир |
|---|---:|
| Чтение, установка и первый запуск | 25–45 мин |
| Мини-ТЗ, алгоритм и ожидаемый вывод | 15–20 мин |
| Своя версия и два изменения требований | 20–30 мин |
| Расследование ошибки | 15–20 мин |
| Первый коммит и заметка о результате | 15–25 мин |

## Сделай по шагам

1. В отдельной папке проекта используй `go mod init jobflow`. В `NOTES.md` запиши, кому нужна программа, какие три дела показываем и почему именно в этом порядке. Укажи, чего первая версия пока не делает.
2. Сформулируй инвариант: ни одно согласованное дело не пропускается и не дублируется. Запиши алгоритм и ожидаемый вывод **до кода**.
3. Реализуй вывод, запусти через `go run .`, сравни построчно. Затем заказчик меняет второе дело и просит перенести его наверх. Обнови сначала ожидание, потом код. Второе изменение: убрать одно дело, которое уже выполнено. Сейчас это ручное изменение исходника; автоматическое правило появится на уроке 3.
4. Намеренно нарушь инвариант дубликатом. Объясни, почему сборка успешна. Отдельно создай опечатку в имени функции, сохрани первое сообщение ошибки и исправь. Верни верную итоговую версию с двумя оставшимися делами.
5. По [памятке Git](../docs/GIT.md#первый-коммит-в-своём-jobflow) сохрани исходники, `go.mod`, `.gitignore`, заметку и краткий README с командой запуска. Просмотри `git diff --cached` перед коммитом.

## Что сдавать и как принимаем

Ссылка на коммит или PR; в README — команда запуска и актуальный ожидаемый вывод. В `NOTES.md` — исходное ТЗ, две его правки, инвариант, один случай «собралось, но неверно» и один сбой сборки. Не нужен длинный отчёт: по 1–2 предложения на пункт достаточно.

Ментор просит внести ещё одно изменение порядка и объяснить, какой пример теперь проверяем. Программа должна повторно запускаться из описанной папки. Открытая проверка первого этапа подтверждает только запуск и непустой вывод; порядок твоих дел и ход рассуждения оцениваем на ревью.

<details><summary>Застрял: с чего начать ТЗ?</summary>

«Когда я запускаю программу, хочу увидеть … . Порядок … . Если меняем список, сохраняем …». Заполни пропуски конкретными данными. Затем напиши ожидаемый экран обычным текстом.

</details>

<details><summary>Изменил файл, вывод прежний</summary>

Сохранён ли файл? Совпадает ли папка терминала с папкой редактора? Что показывает список файлов? Изменяй по одному фактору и повторяй команду.

</details>

**★ По желанию, 15–30 минут:** предложи две версии подачи одного плана — деловую и с характером. Попроси знакомого выбрать понятную. Запиши, что в оформлении помогло, а что отвлекло. Исходный логотип курса менять для этого не нужно.
