# 21. Практика: Как выпустить новую версию и спокойно её остановить?

## Задание: выпуск без шаманства

**3–5 часов.** План выпуска/отката — около часа, наблюдения за запуском и остановкой — 1–2 часа, совместимость схемы и runbook — ещё час. Базовую установку Docker повторять не нужно.

1. Собери образ одной версии с включёнными миграциями. Покажи, что runtime содержит бинарник и не требует cmd/migrate/каталога SQL. Зафиксируй выбранную версию сборки в отчёте.
2. Продемонстрируй готовность после миграций, ошибку неверного DSN, неуспешный старт при ошибке миграции в отдельной базе. Сопоставь состояние контейнера, код выхода и журнал.
3. Запусти запрос и фоновую задачу, останови app штатным SIGTERM. Проследи порядок отмены, ожидания работников и закрытия пула. Опиши ограничение: зависший обработчик обязан уважать context.
4. Составь план добавления нового поля без поломки старой версии: совместимое расширение, обновление кода, заполнение, ужесточение. Отдельно опиши откат бинарника; Down автоматически не вызывается.
5. Напиши runbook: симптомы недоступной базы, таймаута миграции, занятого порта; команды ps/logs; где данные и резервная копия; кто и когда принимает решение об откате. Секреты в отчёт не включай.

**Готово, когда:** новый код появляется после build, сервис не принимает работу до миграций, обычная остановка сохраняет том, журнал позволяет найти конкретный запрос/job, собственные ограничения runner описаны честно. Снимок 21 — учебный одиночный экземпляр, не обещание произвольного горизонтального масштабирования.

**★ По желанию:** измерь длительность конкретного изменения схемы на увеличенном наборе учебных данных и объясни, почему нельзя просто увеличить startup timeout без анализа блокировок.
