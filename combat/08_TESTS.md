# 08. Практика: Исправили одно. Как проверить остальное?

## Задание: страховка перед следующим изменением

**3–5 часов.** Не заполняем время процентом покрытия: проектируем наблюдения, которые поймают реальные поломки. Около часа на таблицу и первые тесты, 1–2 часа на сценарии состояния, остальное на сообщения, эксперимент и исправления.

1. Для модели в pkg создай табличные проверки валидного ввода, пробельных значений, приоритетов 0/1/3/4. Ожидания явные, без копирования формулы Validate.
2. Проверь копию Task и Complete. Для хранилища покрой дубликат с последующим чтением, изменение неизвестного ID и удаление без потери соседней задачи. Каждый случай создаёт своё состояние.
3. Для каждого теста укажи защищаемый инвариант. Сообщение падения должно показывать вход, ожидание и факт.
4. В отдельной ветке убери проверку дубликата, запусти соответствующий тест и сохрани первое понятное сообщение падения. Верни правильную реализацию. В итоговой ветке намеренной поломки нет.
5. Выполни go test ./... и посмотри coverage-отчёт. Найди один незащищённый сценарий, даже если процент красивый. Приложи вывод и объяснение.

**Готово, когда:** проверки независимы от порядка map и запуска друг друга; ошибка проверяется по смыслу; отказ проверяется вместе с состоянием; намеренная поломка замечена. Нет обязательного порога 80% ради числа.

Эталон 08 демонстрирует два теста модели в pkg. Твоя задача шире: выбрать и проверить недостающие истории. Ментор оценивает качество наблюдений; открытый набор не объявлен исчерпывающим.

<details><summary>Если тест всегда зелёный</summary>

Посмотри, есть ли assert результата после вызова. Затем проверь, что твоя намеренная поломка действительно затронула выбранный вход. Тест, проверяющий только err != nil, может не заметить порчу данных.

</details>

**★ По желанию:** добавь fuzz-проверку Validate с понятным свойством. Не утверждай, что отсутствие найденной ошибки означает доказанную корректность.
