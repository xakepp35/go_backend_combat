# 1. Общие правила

Цель контрольной — проверить не знание отдельных конструкций Go, а способность из требований получить корректную работающую программу.

Для каждой задачи важны:

- наблюдаемое поведение;
- корректные состояния и переходы;
- семантика ошибок;
- границы ответственности;
- корректность конкурентного выполнения, если оно присутствует;
- возможность доказать требуемые свойства тестами.

Используйте только стандартную библиотеку Go.

Каждую задачу рекомендуется выполнять в отдельном package:

```text
control/
├── task01/
├── task02/
├── task03/
├── task04/
├── task05/
└── task06/
```

`main()` писать не требуется, если он не нужен для решения.

Итоговый код должен проходить:

```bash
go fmt ./...
go test ./...
go test -race ./...
go vet ./...
```

Конкретный внутренний способ реализации в большинстве задач **не задан намеренно**.

Если несколько вариантов реализации удовлетворяют контракту — допустим любой из них.

Главное правило контрольной:

> Сначала понять, какое поведение необходимо гарантировать. Затем выбрать механизм, который эту гарантию обеспечивает.

# Задача 1. Device Registry

**Ориентир по времени: 10–15 минут.**

Необходимо реализовать небольшой сервис регистрации устройств.

Устройство описывается структурой:

```go
type Device struct {
	ID   string
	Kind string
}
```

Известны следующие ошибки:

```go
var (
	ErrInvalidDevice = errors.New("invalid device")
	ErrAlreadyExists = errors.New("device already exists")
	ErrNotFound      = errors.New("device not found")
)
```

## Требование

Программа должна позволять:

1. зарегистрировать новое устройство;
2. получить зарегистрированное устройство по его `ID`.

Устройство считается корректным только тогда, когда одновременно выполняются условия:

```text
ID   != ""
Kind != ""
```

Пустой `ID` или пустой `Kind` означает некорректное устройство.

---

## Регистрация

Реализуйте операцию:

```go
Register(id string, kind string) (Device, error)
```

Успешная регистрация должна:

1. создать значение `Device`;
2. проверить его корректность;
3. сохранить устройство;
4. вернуть созданное устройство.

Например:

```go
device, err := service.Register("dev-1", "sensor")
```

при успешном выполнении должно привести к состоянию:

```text
device.ID   == "dev-1"
device.Kind == "sensor"
err         == nil
```

---

## Ошибочные сценарии

### Некорректное устройство

Например:

```go
service.Register("", "sensor")
```

или:

```go
service.Register("dev-1", "")
```

должно завершиться ошибкой, для которой:

```go
errors.Is(err, ErrInvalidDevice) == true
```

Некорректное устройство не должно попадать в repository.

### Повторная регистрация

После:

```go
service.Register("dev-1", "sensor")
```

повторная регистрация:

```go
service.Register("dev-1", "camera")
```

должна вернуть ошибку, для которой:

```go
errors.Is(err, ErrAlreadyExists) == true
```

Первое сохранённое устройство при этом не должно измениться.

---

## Получение устройства

Должна существовать операция получения устройства:

```go
Get(id string) (Device, error)
```

Для существующего `ID` возвращается сохранённое устройство.

Для неизвестного `ID` должна возвращаться ошибка, для которой:

```go
errors.Is(err, ErrNotFound) == true
```

---

## Дополнительное требование к конструкции

Хранилище реализуйте в памяти.

При этом бизнес-логика регистрации не должна быть привязана к конкретному способу хранения данных.

Представьте, что завтра вместо памяти будет использоваться другое хранилище. Код самой операции регистрации при такой замене изменяться не должен.

---

## Tests

Напишите table-driven tests как минимум для следующих сценариев:

```text
успешная регистрация
пустой ID
пустой Kind
повторный ID
получение существующего устройства
получение неизвестного устройства
```

Тестирование ошибок должно проверять их **identity**, а не сравнивать только текст ошибки.

# Задача 2. Concurrent Tracker

**Ориентир по времени: 15 минут.**

Есть система, которая одновременно выполняет некоторое количество независимых работ.

Необходимо реализовать объект `Tracker`, который хранит текущее состояние этих работ.

Снимок состояния описывается структурой:

```go
type Snapshot struct {
	Pending int
	Running int
	Done    int
	Failed  int
}
```

Реализуйте:

```go
type Tracker struct {
	// ваша реализация
}

func NewTracker(total int) *Tracker

func (t *Tracker) Start() bool

func (t *Tracker) Finish(success bool) error

func (t *Tracker) Snapshot() Snapshot
```

Также объявите:

```go
var ErrNothingRunning = errors.New("nothing running")
```

---

## Начальное состояние

После:

```go
tracker := NewTracker(100)
```

состояние должно быть:

```text
Pending = 100
Running = 0
Done    = 0
Failed  = 0
```

`total` задаётся один раз при создании `Tracker` и далее не изменяется.

---

## Start

Метод:

```go
tracker.Start()
```

означает попытку взять одну ожидающую работу в выполнение.

Если существуют ожидающие работы:

```text
Pending > 0
```

операция должна атомарно выполнить переход:

```text
Pending -= 1
Running += 1
```

и вернуть:

```go
true
```

Если ожидающих работ больше нет:

```text
Pending == 0
```

метод должен:

```text
не менять состояние
вернуть false
```

---

## Finish

Метод:

```go
tracker.Finish(true)
```

означает успешное завершение одной выполняющейся работы.

Состояние изменяется:

```text
Running -= 1
Done    += 1
```

Метод:

```go
tracker.Finish(false)
```

означает неуспешное завершение работы:

```text
Running -= 1
Failed  += 1
```

Если выполняющихся работ нет:

```text
Running == 0
```

`Finish` не должен менять состояние и должен вернуть ошибку:

```go
errors.Is(err, ErrNothingRunning) == true
```

---

## Snapshot

Метод:

```go
snapshot := tracker.Snapshot()
```

возвращает состояние системы на некоторый единый момент времени.

Получатель не должен увидеть, например, половину одного перехода:

```text
Pending уже уменьшился,
а Running ещё не увеличился.
```

---

## Главный инвариант

В любой момент времени должно выполняться:

```text
Pending >= 0
Running >= 0
Done    >= 0
Failed  >= 0
```

и:

```text
Pending + Running + Done + Failed == total
```

Эти свойства должны сохраняться независимо от порядка concurrent-вызовов.

---

## Concurrency requirement

Следующие методы могут одновременно вызываться различными goroutines:

```text
Start
Finish
Snapshot
```

Решение должно быть корректным при таком использовании и проходить:

```bash
go test -race ./...
```

---

## Проверочный сценарий

Создайте:

```go
tracker := NewTracker(100)
```

После этого:

- 100 работ должны успешно перейти в `Running`;
- 90 работ должны завершиться успешно;
- 10 — с ошибкой;
- параллельно другая goroutine может многократно читать `Snapshot()`.

Финальное состояние должно быть строго:

```text
Pending = 0
Running = 0
Done    = 90
Failed  = 10
```

Ни один полученный во время работы `Snapshot` не должен нарушать основной инвариант.

# Задача 3. Concurrent Job Runner

**Ориентир по времени: 20 минут.**

Необходимо обработать набор независимых работ параллельно.

При этом количество одновременно выполняемых работ должно быть ограничено.

Дана модель:

```go
type Job struct {
	ID int
}
```

Реализуйте:

```go
var ErrInvalidWorkerCount = errors.New("invalid worker count")
```

и функцию:

```go
func Run(
	ctx context.Context,
	workers int,
	jobs []Job,
	process func(context.Context, Job) error,
) error
```

---

## Что должна делать Run

Например:

```go
jobs := []Job{
	{ID: 1},
	{ID: 2},
	{ID: 3},
	{ID: 4},
	{ID: 5},
}
```

и:

```go
Run(ctx, 2, jobs, process)
```

означает:

> необходимо обработать пять `Job`, но одновременно внутри `process` могут находиться не более двух вызовов.

Количество `jobs` никак не должно увеличивать заданный предел concurrency.

---

## Некорректное количество workers

Если:

```text
workers <= 0
```

функция должна немедленно завершиться ошибкой, для которой:

```go
errors.Is(err, ErrInvalidWorkerCount) == true
```

Ни один `Job` в этом случае обрабатываться не должен.

---

## Нормальное выполнение

Если `ctx` не отменён и `process` не возвращает ошибок:

1. каждый `Job` должен быть передан в `process`;
2. каждый `Job` должен быть передан туда ровно один раз;
3. одновременно должно выполняться не более `workers` вызовов `process`;
4. `Run` не должна возвращаться раньше завершения всей начатой ею работы;
5. после возврата из `Run` не должно оставаться goroutines, жизненным циклом которых владел этот вызов `Run`.

Порядок обработки `Job` не определён.

То есть программа не должна предполагать:

```text
1 → 2 → 3 → 4 → 5
```

Допустим, например:

```text
2 → 1 → 4 → 3 → 5
```

---

## Ошибка process

Функция:

```go
process(ctx, job)
```

может вернуть ошибку.

Если хотя бы одна обработка завершилась ошибкой, вызывающая сторона должна иметь возможность узнать об этом через результат `Run`.

Не требуется прекращать весь batch после первой обычной ошибки `process`.

Уже принятые работы разрешено закончить.

---

## Cancellation

`ctx` является внешним сигналом прекращения работы.

После того как `Run` обнаружила отмену контекста:

- новые `Job` больше не должны передаваться в обработку;
- уже начатые вызовы `process` должны получить тот же `ctx`;
- `Run` должна дождаться завершения принадлежащих ей goroutines;
- после этого `Run` должна вернуть ошибку контекста.

То есть корректный lifecycle выглядит так:

```text
Run owns concurrent work
        ↓
ctx cancelled
        ↓
stop accepting new work
        ↓
started work terminates
        ↓
owned goroutines terminate
        ↓
Run returns
```

Отмена контекста не должна превращаться в goroutine leak.

---

## Tests

Напишите tests, которые доказывают минимум четыре свойства.

### 1. Вся работа выполнена

```text
20 jobs
workers = 4
```

Все 20 `Job` должны быть обработаны ровно один раз.

### 2. Ограничение concurrency

Во время теста измерьте реальное количество одновременно выполняющихся вызовов `process`.

Должно выполняться:

```text
maxConcurrent <= 4
```

### 3. Ошибка обработки наблюдаема

Если `process` для одного `Job` возвращает некоторую заранее известную ошибку:

```go
var ErrProcess = errors.New("process failed")
```

после завершения `Run` вызывающая сторона должна суметь обнаружить эту ошибку.

### 4. Cancellation

Создайте сценарий, в котором часть работы занимает заметное время, отмените `ctx` и убедитесь, что:

```text
Run завершается
ошибка context наблюдаема
owned goroutines завершились
```

# Задача 4. Registration Service Refactoring

**Ориентир по времени: 15 минут.**

В проекте появился следующий сервис:

```go
type User struct {
	ID   string
	Name string
}

type RegistrationService struct {
	repository *MemoryUserRepository
	audit      *ConsoleAudit
}

func (s *RegistrationService) Register(
	ctx context.Context,
	user User,
) error {
	if user.ID == "" || user.Name == "" {
		return ErrInvalidUser
	}

	if err := s.repository.Add(ctx, user); err != nil {
		return fmt.Errorf("save user: %w", err)
	}

	if err := s.audit.Write(
		ctx,
		"user_registered",
		user.ID,
	); err != nil {
		return fmt.Errorf("write audit: %w", err)
	}

	return nil
}
```

Проблема стала заметна после роста проекта.

`MemoryUserRepository` содержит:

```go
Add(...)
Get(...)
Delete(...)
List(...)
Reset(...)
Dump(...)
Stats(...)
```

Хотя `RegistrationService` использует только:

```text
Add
```

`ConsoleAudit` содержит:

```go
Write(...)
Open(...)
Close(...)
Flush(...)
Rotate(...)
Stats(...)
```

Хотя сервису нужен только:

```text
Write
```

---

## Задание

Перепроектируйте `RegistrationService`, сохранив его внешнее поведение.

После рефакторинга должны выполняться следующие change scenarios.

---

## Change A — другое хранилище

Сегодня используется:

```text
MemoryUserRepository
```

Завтра появляется:

```text
PostgresUserRepository
```

или любая другая реализация хранения пользователей.

Код `RegistrationService.Register` изменяться не должен.

---

## Change B — другой audit

Сегодня используется:

```text
ConsoleAudit
```

Завтра события необходимо отправлять в другую систему.

Логика `RegistrationService.Register` изменяться не должна.

---

## Change C — рост repository

В конкретном repository появляются ещё десять методов.

Это не должно автоматически увеличивать количество операций repository, от которых зависит `RegistrationService`.

---

## Change D — рост audit implementation

В concrete audit implementation появляются дополнительные возможности.

Они не должны становиться частью dependency surface сервиса только потому, что существуют.

---

## Поведение Register

Существующее поведение необходимо сохранить полностью.

### Некорректный User

Если:

```text
ID == ""
```

или:

```text
Name == ""
```

должно выполняться:

```text
repository не вызывается
audit не вызывается
errors.Is(err, ErrInvalidUser) == true
```

### Ошибка repository

Если сохранение пользователя завершилось ошибкой:

```text
audit не вызывается
ошибка repository остаётся распознаваемой через errors.Is
```

### Ошибка audit

Если пользователь успешно сохранён, но audit завершился ошибкой:

```text
пользователь уже считается сохранённым
Register возвращает ошибку audit
identity исходной ошибки сохраняется
```

Откатывать успешное сохранение пользователя не требуется.

### Полный успех

Если обе операции успешны:

```go
err == nil
```

---

## Composition

Конкретные реализации зависимостей должны передаваться сервису снаружи.

Сам сервис не должен создавать себе:

```text
MemoryUserRepository
ConsoleAudit
```

---

## Tests

Напишите tests без использования реальных:

```text
MemoryUserRepository
ConsoleAudit
```

Тест должен иметь возможность явно проверить:

```text
был ли вызван repository
был ли вызван audit
какие аргументы были переданы
что произошло при ошибке каждой зависимости
```

# Задача 5. Event Router

**Ориентир по времени: 10–15 минут.**

Система получает события нескольких типов.

Модель события:

```go
type Event struct {
	ID      string
	Kind    string
	Payload []byte
}
```

Первоначально система знает два типа:

```text
email
webhook
```

У каждого типа своя реализация обработки.

Необходимо построить `Router`, который выбирает нужную реализацию в зависимости от `Event.Kind`.

---

## Dispatch

Реализуйте:

```go
func (r *Router) Dispatch(
	ctx context.Context,
	event Event,
) error
```

---

## Поведение

Для:

```go
Event{
	ID:   "event-1",
	Kind: "email",
}
```

должен быть вызван обработчик `email`.

При этом `webhook`-обработчик вызван быть не должен.

Для:

```go
Event{
	ID:   "event-2",
	Kind: "webhook",
}
```

должен быть вызван только соответствующий обработчик.

---

## Неизвестный тип

Объявите:

```go
var ErrUnsupportedEvent = errors.New("unsupported event")
```

Если:

```go
event.Kind == "something-unknown"
```

`Dispatch` должен завершиться ошибкой, для которой:

```go
errors.Is(err, ErrUnsupportedEvent) == true
```

Ни один зарегистрированный обработчик при этом вызываться не должен.

---

## Ошибка обработчика

Обработчик может вернуть ошибку.

Например:

```go
var ErrDelivery = errors.New("delivery failed")
```

Если выбранный обработчик возвращает `ErrDelivery`, вызывающая сторона после `Dispatch` должна иметь возможность проверить:

```go
errors.Is(err, ErrDelivery) == true
```

Дополнительный контекст ошибки разрешён.

---

## Главное требование изменения

После того как `Router` закончен и протестирован, появляется новое требование:

```text
поддержать Kind == "sms"
```

Вы должны иметь возможность:

1. написать новую реализацию обработчика;
2. подключить её при сборке приложения;
3. отправить событие `sms`;

при этом алгоритм самого `Dispatch` изменять не требуется.

После этого точно так же может появиться:

```text
push
telegram
internal
...
```

Добавление новой реализации не должно приводить к постоянному переписыванию стабильного алгоритма маршрутизации.

---

## Tests

Докажите как минимум:

```text
email вызывает только email handler

webhook вызывает только webhook handler

unknown kind возвращает ErrUnsupportedEvent

ошибка handler сохраняет identity

новый тип обработчика можно подключить без изменения алгоритма Dispatch
```

# Задача 6 ★. Combat Dispatcher

**Задача повышенной сложности.**

Эта задача продолжает №5.

Есть уже работающий `Router`, который умеет обработать одно событие:

```go
r.Dispatch(ctx, event)
```

Теперь система должна уметь обрабатывать сразу большую пачку событий.

Необходимо добавить:

```go
func (r *Router) DispatchBatch(
	ctx context.Context,
	workers int,
	events []Event,
) (BatchStats, error)
```

Статистика результата:

```go
type BatchStats struct {
	Started   int
	Succeeded int
	Failed    int
}
```

---

## Общая задача

Например, поступило:

```text
1000 events
```

Но система настроена:

```text
workers = 5
```

Это означает:

> сколько бы событий ни пришло, одновременно выполняться могут не более пяти обработчиков.

При этом для выбора обработчика должна использоваться уже существующая логика `Router`.

Batch-processing не должен создавать второй независимый механизм определения:

```text
email
webhook
sms
...
```

---

## Started

Событие считается `Started` в тот момент, когда система действительно начала его обработку.

Событие, до которого выполнение не дошло из-за cancellation, в `Started` не входит.

Каждое событие может быть начато не более одного раза.

---

## Succeeded

Если обработчик события вернул:

```go
nil
```

увеличивается:

```text
Succeeded
```

---

## Failed

Если обработка началась, но завершилась ошибкой, увеличивается:

```text
Failed
```

В том числе ошибкой считается ситуация, когда для события невозможно найти подходящий handler.

---

## Главный инвариант статистики

После завершения `DispatchBatch` всегда должно выполняться:

```text
Started == Succeeded + Failed
```

То есть каждое начатое событие после завершения batch имеет ровно один конечный результат:

```text
success
```

или:

```text
failure
```

---

## Полностью успешный batch

Для:

```text
len(events) == 100
```

если все обработчики завершились успешно и контекст не отменялся:

```text
Started   == 100
Succeeded == 100
Failed    == 0
err       == nil
```

---

## Ограничение concurrency

Для:

```text
workers == 5
```

одновременно могут выполняться максимум пять обработчиков.

Это требование должно выполняться даже если:

```text
len(events) == 100
```

или:

```text
len(events) == 100_000
```

Количество входных событий не является разрешением создать такое же количество одновременно выполняющейся работы.

---

## Ошибки отдельных событий

Ошибка одного обработчика не должна автоматически прекращать обработку всей пачки.

Например:

```text
event-1 → success
event-2 → failure
event-3 → success
event-4 → success
```

должно привести к статистике:

```text
Started   = 4
Succeeded = 3
Failed    = 1
```

Через возвращаемую ошибку вызывающая сторона должна иметь возможность понять, что batch содержал неуспешную обработку.

Конкретный способ представления нескольких ошибок выберите самостоятельно.

---

## Cancellation

`ctx` может быть отменён во время обработки batch.

После того как `DispatchBatch` обнаружил отмену:

```text
новые события больше не начинают обработку
```

Уже начатая работа:

```text
получает тот же ctx
завершается
учитывается в BatchStats
```

После этого:

```text
все принадлежащие DispatchBatch goroutines завершены
DispatchBatch возвращает управление
ошибка context наблюдаема вызывающей стороной
```

События, обработка которых не начиналась, в статистику не входят.

Поэтому при cancellation допустимо:

```text
Started < len(events)
```

но по-прежнему обязательно:

```text
Started == Succeeded + Failed
```

после завершения всей начатой работы.

---

## Ownership

После возврата:

```go
stats, err := router.DispatchBatch(...)
```

не должно оставаться фоновой работы, жизненным циклом которой владел этот вызов.

То есть возврат из функции означает не:

> «я попросил goroutines когда-нибудь закончить»,

а:

> «вся работа, которую этот вызов успел начать, уже завершила свой lifecycle».

---

## Последнее изменение требований

После завершения задачи заказчик говорит:

> Теперь нам нужен `push`.

Вы добавляете новый handler:

```text
push
```

Batch-processing менять не требуется.

Он должен автоматически уметь обрабатывать новый тип через тот же механизм маршрутизации, который используется для одиночного:

```go
Dispatch(...)
```

---

## Verification

Напишите tests минимум для следующих сценариев.

### A. Bounded concurrency

```text
events  = 100
workers = 5
```

Во время теста измерьте максимальное количество одновременно работающих handlers.

Должно выполняться:

```text
maxConcurrent <= 5
```

---

### B. Mixed batch

Пачка содержит:

```text
email
webhook
email
webhook
...
```

Все события успешно обрабатываются соответствующими handlers.

Ожидается:

```text
Started   == len(events)
Succeeded == len(events)
Failed    == 0
```

---

### C. Handler failures

Часть handlers возвращает ошибки.

После завершения:

```text
Started == Succeeded + Failed
Failed > 0
```

Ошибка batch должна быть наблюдаема вызывающей стороной.

---

### D. Unsupported event

Часть событий имеет неизвестный `Kind`.

Такие начатые события учитываются как:

```text
Failed
```

---

### E. Cancellation

Отмените `ctx` во время выполнения.

Проверьте:

```text
DispatchBatch завершилась
ошибка context наблюдаема
новая работа после остановки приёма не запускается
вся начатая работа завершена
Started == Succeeded + Failed
```

---

### F. Extension

Подключите новый тип:

```text
push
```

Не изменяя алгоритмы:

```go
Dispatch
DispatchBatch
```

убедитесь, что события нового типа начали обрабатываться.

---

# Итоговая проверка

После выполнения контрольной запустите:

```bash
go fmt ./...
go test ./...
go test -race ./...
go vet ./...
```

Работа считается корректной только тогда, когда выполняется не один happy path, а весь заданный контракт.

Для каждой задачи задайте себе пять вопросов:

```text
1. Какое наблюдаемое поведение требуется?

2. Какое состояние никогда не должно стать некорректным?

3. Что происходит при ошибке?

4. Кто владеет состоянием, зависимостью или concurrent work?

5. Каким тестом я могу доказать, что требование действительно выполнено?
```

## Критерий результата

```text
код компилируется
        +
behavior выполнен
        +
инварианты сохранены
        +
ошибки имеют корректную семантику
        +
concurrent code race-free
        +
lifecycle завершён
        +
границы зависимостей позволяют заявленные изменения
        +
tests это доказывают
```

> **Работающий код — начало ответа. Инженерный ответ заканчивается доказанной гарантией.**
