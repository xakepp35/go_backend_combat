# 03. Практика: планировщик без лишних напоминаний

[Карта курса](../course/README.md) · [← Предыдущая практика](02_VALUES.md) · [Следующая →](04_FUNCTIONS.md)

Теперь JobFlow должен объяснять, какое дело требует внимания. **Ориентир: 2–4 часа:** правила и таблица 25–35 минут, код 45–75, граничные случаи 25–40, Git-конфликт 30–40, заметки и исправления 15–25. Если опыт уже есть, нижняя граница естественна.

## Обязательный результат

Добавь к плану прошлого этапа блок обработки одного выбранного дела: `title`, `priority`, `done`, `reminders`. Данные пока задаются в коде.

1. До любых напоминаний проверь непустое название (`title == ""` достаточно для этого этапа), приоритет 1..3 и число повторов 0..3. Неверный ввод заканчивается понятным отказом. Проверку названий из одних пробелов усилим вместе со строками и ошибками.
2. Выполненное дело получает отметку «Уже выполнено» и не напоминается. Для невыполненного приоритет 1 означает обычное дело, 2–3 — срочное.
3. Выведи ровно заданное число пронумерованных напоминаний, каждое с названием дела. Ноль допустим. В отчёте бюджета из прошлого этапа замени `true/false` понятной фразой: «План помещается» или «Перегрузка на N минут».
4. Сохрани расчёт времени отдельным участком перед обработкой напоминаний, чтобы ранний `return` не скрывал уже согласованный отчёт плана.

**Инварианты:** неверный ввод и выполненное дело не создают напоминаний; число повторов соответствует принятому значению; расчёт времени из прошлого этапа остаётся верным.

## Самостоятельная проверка

Таблица минимум из восьми случаев: приоритеты 0/1/2/3/4, выполненное дело, ноль повторов, отрицательное число и число больше лимита. Один случай может защищать несколько границ. Для выполненного дела с неверным приоритетом договорись, что важнее: здесь сначала отвергаем неверные данные.

Для каждого случая укажи вход, ожидаемый исход и наблюдение. Неверное число повторов не должно «молча исправляться» на три: это скрывает ошибку пользователя. Намеренно замени `<=` на `<` в цикле, найди минимальный пример, который замечает поломку, затем верни правильную версию.

Пройди [Git-лабораторию с конфликтом](../docs/GIT.md#лаборатория-2-расхождение-и-конфликт) **в отдельном репозитории**. На ревью покажи граф и объясни, почему обе версии нельзя было объединить автоматически. Снимок экрана необязателен; подойдёт текст `git log --graph --oneline --all`.

Открытые проверки этапа подтверждают запуск и наличие условия/цикла. Всю таблицу поведения нужно проверить руками; зелёный запуск не заменяет её.
