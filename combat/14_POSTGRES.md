# 14. Практика: Как Go разговаривает с базой?

## Задание: один запуск поднимает код и его схему

**4–6 часов.** Подключение и пул — около часа; адаптер операций — 1–2 часа; встроенный Goose и запуск — 1–2 часа; итоговые истории/исправления — ещё час. Это комплексная работа, а не переписывание одного SELECT.

1. Реализуй Postgres-адаптер через pgxpool/v5 за портом из pkg/ports.go. Приложение использует публичные req/res-объекты, API зависит от интерфейса сервиса. Сохрани прежнее поведение CRUD.
2. Параметризуй SQL, освобождай rows, проверяй rows.Err и RowsAffected, переводь ErrNoRows/SQLSTATE в общие ошибки. Не прячь недоступную БД под ErrNotFound.
3. Подключи goose/v3, добавь Up/Down в SQL, включи их в embed.FS. Используй Provider и session advisory lock по reference14. Не добавляй cmd/migrate и сервис мигратора.
4. В старте: пул → Ping → Goose → HTTP. При ошибке миграции процесс завершается с ненулевым кодом; успешный restart пропускает уже применённые версии. Таймаут ограничивает старт.
5. Удали runtime-копирование SQL из Dockerfile, если оно осталось. Собери образ и запусти через Compose. Создай задачу, перезапусти app, прочитай её. Посмотри goose_db_version через psql.
6. В отдельной **пустой лабораторной базе** покажи отказ новой заведомо ошибочной миграции: HTTP не должен начать принимать запросы. Не порть применённый файл и рабочие данные. Верни корректную ветку.

**Сдаёшь:** код, схему зависимостей, инструкцию запуска, истории успешного повторного старта и отказа, объяснение адаптера stdlib.OpenDBFromPool. Старая история course_migrations требует явного переноса по памятке, не удаления тома.

Эталон 14 использует pgxpool, встроенный Goose и публичные объектные контракты pkg. Существующие проверки вызывают TaskRepository и проверяют операции и повторное применение Goose. Архитектуру, объяснение контрактов и порядок HTTP-старта отдельно смотрит ментор. После текущего изменения сигнатур наборы ещё не запускались.

**★ По желанию:** запусти два процесса, применяющих миграции к отдельной лабораторной базе, и объясни роль advisory lock. Это опыт про миграции; с 20 два фоновых runner не запускаем без протокола владения jobs.
