# 09. Практика: На моей машине работает. А на твоей?

## Задание: твой проект переезжает

**3–5 часов после установки Docker.** Около часа на упаковку и разбор файлов, час на Compose и базу, час на сетевую/операционную диагностику; остаток — инструкция и исправления. Медленная загрузка образов не должна превращаться в шестичасовой экзамен.

1. Размести точку входа в cmd/jobflow, сохрани существующую модель и проверки. Собери Dockerfile с двумя стадиями и непривилегированным runtime. Изучи .dockerignore и исключи локальный .env.
2. Добавь compose.yaml: разовая app и PostgreSQL 18 с томом, локальной публикацией порта и healthcheck. Запусти app через `docker compose run --rm --build app`, базу — через `up -d --wait postgres`.
3. Выполни SELECT version() через psql **в контейнере**. Запиши адрес базы для приложения на хосте и для приложения в Compose. Go пока не подключаем к ней.
4. Останови окружение через down без -v и подними postgres снова. Найди прежний именованный том через `docker volume ls`. Сохранность записей подробно проверим на SQL-неделе; один список томов её ещё не доказывает.
5. Измени сообщение консольной программы и покажи его после пересборки. Объясни разницу между restart и build.
6. Напиши README своего проекта: требования, запуск, остановка, где лежат данные, как читать логи, что делать при занятом порте. Попроси ментора пройти инструкцию без устных подсказок.

**Приёмка:** программа собирается в образ, одноразовый контейнер завершается успешно, PostgreSQL healthy, порт опубликован только локально, `.env` не в коммите, инструкция различает штатную остановку и удаление данных. Никакого ручного создания go.mod и отдельной установки PostgreSQL на хост.

Go-проверки 09 охраняют поведение старого хранилища и не проверяют Dockerfile/Compose. Окружение проверяется отдельным просмотром запуска с ментором; не называй успешный go test проверкой контейнерной сети.
